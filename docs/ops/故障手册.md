# 故障手册

适用范围：单机 Docker Compose 部署，仓库根目录有 `.env`。排障先检查容器状态和日志，再处理数据；不要使用 `docker compose down -v`，也不要删除 PostgreSQL/MinIO 卷。

## 从全停状态恢复

按依赖顺序启动，服务名对应 `deploy/docker-compose.prod.yml`：

```bash
docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d postgres redis
docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d rocketmq-namesrv rocketmq-broker minio
docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d ai app web
docker compose -f deploy/docker-compose.prod.yml --env-file .env ps
curl -fsS http://127.0.0.1/healthz
```

确认 PostgreSQL、Redis、RocketMQ、MinIO 和 `ai/app/web` 均处于 healthy/running；再通过浏览器尝试登录。

## 1. 判题一直排队或判题卡住

1. 查看 `app` 和 PostgreSQL：

   ```bash
   docker logs --tail=200 codelab-app
   docker exec codelab-pg psql -U "${POSTGRES_USER:-codelab}" -d "${POSTGRES_DB:-codelab}" -c "SELECT status, count(*) FROM judge_queue GROUP BY status;"
   ```

2. 检查 `.env` 的 `APP_JUDGE_ENABLED`、并发数与队列上限；确认 app healthy，数据库连接可用。
3. 若队列任务持续停在 queued/running，先保存 submission id、队列记录和 app 日志，再重启 app：

   ```bash
   docker compose -f deploy/docker-compose.prod.yml --env-file .env restart app
   ```

4. 只清理确认已经终止的过期工作目录；保持 `judge` 低权限、超时和输出限制，不要改为 root 运行。反复出现时将队列记录与日志交给维护人员处理，不直接删除队列行。

## 2. AI 请求返回 502

1. 检查服务与内部连通性：

   ```bash
   docker compose -f deploy/docker-compose.prod.yml --env-file .env ps ai app
   docker logs --tail=200 codelab-ai
   docker logs --tail=200 codelab-app
   ```

2. 生产环境确认 `.env` 的 `AI_PROVIDER=openai`、`DASHSCOPE_API_KEY` 有效，模型名、端点和账号额度正确；stub 只用于开发/演示。
3. 确认 `AI_INTERNAL_TOKEN` 在 app/ai 两侧一致。修改 `.env` 后重建相关容器：

   ```bash
   docker compose -f deploy/docker-compose.prod.yml --env-file .env up -d --force-recreate ai app
   ```

4. 从学生已提交的题目重试；配额 429 属正常限额，不按 502 排障。

## 3. 题目图片返回 404

1. 检查 MinIO 状态、桶和对象是否存在：

   ```bash
   docker compose -f deploy/docker-compose.prod.yml --env-file .env ps minio
   docker logs --tail=100 codelab-minio
   ```

2. 检查 app 的 `MINIO_ENDPOINT`、`MINIO_BUCKET`、`MINIO_ACCESS_KEY`、`MINIO_SECRET_KEY` 是否与服务器配置一致；凭证不要贴到聊天或日志。
3. 图片 API 要求登录，并验证调用者是否有权访问对应题目。先确认资源 ID 和当前账号权限，再判断是否是对象确实缺失。
4. 对象不存在时从原始题目附件重新上传；不要手工修改 `files.object_key` 指向不相关对象。

## 4. 登录后刷新即掉线

1. HTTP 部署时确认 `.env` 的 `APP_COOKIE_SECURE=false`；HTTPS 部署时应启用 Secure cookie 并以同源域名访问。
2. 浏览器必须通过 Nginx 同源入口访问，不能前端走一个端口、API 走另一个跨域地址。
3. 检查浏览器是否拒绝/清除了 refresh cookie，检查 Nginx `/api` 反代及 app 日志。
4. 只有明确会话失效时才重新登录；不要为了排查关闭认证或扩大 CORS。

## 5. 容器 OOM 或主机内存紧张

1. 查看资源峰值和被杀容器：

   ```bash
   docker stats --no-stream
   docker inspect -f '{{.Name}} {{.State.OOMKilled}} {{.State.ExitCode}}' $(docker ps -aq)
   free -h
   ```

2. 优先定位 RocketMQ broker、app 判题并发、ai 进程或 Docker 主机其他服务；查看 `docker logs` 的 OOM 前后记录。
3. 释放无用宿主机进程或停止非平台服务；必要时按 PRD 2C4G 账本降低 RocketMQ/app 的内存和并发设置，再重建单个服务。
4. 不要清理数据库/MinIO 卷来释放空间。若磁盘不足，先通过 `df -h` 和 `docker system df` 查明可清理的构建缓存/旧镜像，避免删除运行卷。

## 恢复后检查

- `docker compose ... ps` 中所有服务健康。
- `curl -fsS http://127.0.0.1/healthz` 成功。
- 以管理员登录，再分别确认教师课程页、学生课程页和已有题图可访问。
- 判题/AI 故障恢复后，用演示账号按部署手册与操作手册做单条人工点验；不要拿生产学生数据做破坏性演练。
